# Geometry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A teacher picks Geometry, then photographs or types a figure, checks the reading and what to predict, and presents it. A transformation plays out after the class drags a ghost to its guess. An invariant question unlocks dragging, and live measurements answer it. Students then drag points and replay.

**Architecture:**
- Geometry is a self-contained module under `src/geometry/`: a zod schema, pure derive functions, a written-value fit, a sketch, questions and playback.
- It joins the `Subject` registry and the `Lesson` union the way ecosystem did.
- The server gets geometry reader, writer and drafter files beside the web ones. The route `if` chains in `server/plugin.ts` become one table keyed by subject, so a fourth subject only adds a row.
- Physics and ecosystem behave exactly as at commit `911d428`.

**Tech Stack:** TypeScript strict, zod 4, Vite 8, Vitest 5, canvas 2D. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-29-subjects-design.md`. Read the "Geometry" section, and in "Decisions after review" the bullets on events chosen at check time, what counts as "played through", and "In geometry, written values win".

## Global Constraints

- TypeScript strict. Prefer `type`. Small pure functions. No `// TODO:` comments.
- TDD with colocated `*.spec.ts`. Strong assertions, and no unexplained literals: name them as constants.
- Physics and ecosystem behave exactly as at `911d428`. `npm run check` passes after every task. No existing spec is edited except where a task names the change.
- Commit only with the user's approval. Otherwise, checkpoint with `git add -A && git write-tree` and record the tree id in the ledger. Commits use Conventional Commits with no AI attribution.
- Never use `/tmp`. Kill any dev server you start. Never print or copy keys. Live runs use `node --env-file=/Users/adamrowe/Projects/board-to-life/.env …`.
- Figures use the same 0–1000 reader grid and `drawingSize` as physics and ecosystem. Points are named as written on the board (A, B, C…). Unnamed points the model needs, such as where two lines cross, get ids `P1`, `P2`, and so on.
- Angles are in degrees. Rotations are counterclockwise as seen on the board, and a clockwise rotation is negative. Because the drawing's y axis points down, every angle helper converts once, in `derive.ts`, and nowhere else.
- Written values win. The fitted figure is what the check screen overlays and what the presenter starts from. If the written values can't all hold, the figure keeps its drawn positions and the check screen names the values.
- Students' replays use questions built from templates. There is no model call in front of the class.

## Review Focus

1. **Degenerate figures:** two points at the same spot, a zero-length segment, or a polygon whose vertices lie on one line. Every derive function must return finite numbers or `null`, never `NaN`, and the presenter must draw nothing for a `null` measurement. Tests are in Task 2.
2. **Written values that contradict each other**, such as triangle angles adding up to 190°, or two written angles at one vertex that disagree. The fit must stop and name the values, never loop or move points wildly. Tests are in Task 3.
3. **A point dragged on top of another point, or off the board.** Measurements stay finite. Dragging is clamped to the drawing. Tests are in Tasks 9 and 10.
4. **A reading that names a point twice, or a polygon or mark that cites a missing point.** Validation names the id. Tests are in Task 1.
5. **A figure with nothing to predict:** no polygon and no transformation, such as a lone circle. The check screen says so and offers no Present. Tests are in Tasks 4 and 8.

### Task 2: Derive functions and transformations

**Files:**
- Create: `src/geometry/derive.ts`
- Test: `src/geometry/derive.spec.ts`

**Interfaces:**
- Consumes: `Figure`, `Transformation` (Task 1).
- Produces:
  - `type Positions = Record<string, { x: number; y: number }>`, and `positionsOf(figure): Positions`.
  - Measurements:
    - `distance(p, q): number`.
    - `angleAt(at, from, to): number | null`. This is the inside angle in [0, 180]. It is `null` when a ray has zero length.
    - `polygonAngles(positions, polygon): (number | null)[]`. These are the interior angles, so the sum of a convex polygon's angles is (n − 2)·180.
    - `angleSum(positions, polygon): number | null`.
    - `area(positions, polygon): number | null`. This uses the shoelace formula, taken as absolute. It is `null` when the vertices are collinear.
    - `perimeter(positions, polygon): number`.
    - `areParallel(positions, a: [string, string], b: [string, string], toleranceDegrees): boolean | null`.
  - Transformations:
    - `imageOf(positions, transformation): Positions`. It returns the image of each vertex of `transformation.polygon`, keyed by the vertex id plus `′` (for example `A′`).
    - `transformAt(positions, transformation, t: number): Positions`. This gives the in-between positions for `t` in [0, 1]:
      - reflect: the shape squashes across the mirror and opens on the other side (perpendicular scale `cos(π·t)`);
      - rotate: by `t·degrees`;
      - translate: by `t` times the arrow;
      - dilate: by `1 + (factor − 1)·t`.
  - Lengths:
    - `MEASURE_SCALE_UNITLESS = 100`: with no written length, a displayed length is drawing units ÷ 100.
    - `displayLength(figure, positions, from, to): { value: number; unit: string | null }`. It scales from the first `length` mark that has a `value`.

- [ ] **Step 1: Write failing tests.**
  - A 3-4-5 right triangle has angles 90, about 36.87 and about 53.13 (to 0.01), an angle sum of 180, area 6 and perimeter 12, in units of your fixture.
  - A square has an angle sum of 360.
  - These cases give `null` and never `NaN`: coincident points, a collinear triangle's area, and `angleAt` with a zero-length ray.
  - Reflecting over the vertical line x = 600 maps (500, 300) to (700, 300).
  - Rotating 90° about (600, 400) maps (700, 400) to (600, 300). That is counterclockwise as seen, because y points down.
  - Translating by an arrow from (100, 100) to (300, 150) adds (200, 50).
  - Dilating by 2 from the origin doubles the area to 4 times the original.
  - `transformAt(…, 0)` equals the original positions, and `transformAt(…, 1)` equals `imageOf` for each kind.
  - Reflecting at `t = 0.5` puts every vertex on the mirror line.
  - `displayLength` with a 5 cm mark on a segment drawn 200 units long shows a 400-unit segment as `{ value: 10, unit: 'cm' }`. With no written length, it shows `{ value: 4, unit: null }`.
- [ ] **Step 2:** Run the tests. Expected: FAIL.
- [ ] **Step 3:** Implement. All the angle maths is done in screen orientation, which is the y-down conversion point named in the Global Constraints.
- [ ] **Step 4:** Run `npx vitest run src/geometry && npm run check`. Expected: PASS.

### Task 3: Written values win

**Files:**
- Create: `src/geometry/fit.ts`
- Test: `src/geometry/fit.spec.ts`

**Interfaces:**
- Produces:
  - `FIT_TOLERANCE_DEGREES = 0.5`, `FIT_TOLERANCE_FRACTION = 0.005`, `FIT_ITERATIONS = 500`.
  - `writtenValueConflicts(figure): string[]`. This is the arithmetic check, run before any fitting. It covers:
    - a polygon whose every angle is written and whose angles don't add up to (n − 2)·180;
    - written angles in one triangle that already reach 180 or more;
    - two different written angles at the same vertex between the same rays.

    The message names each value. For example: "The angles written at A (70°), B (60°) and C (60°) add up to 190°, but a triangle's angles add up to 180°."
  - `fitWrittenValues(figure): { ok: true; figure: Figure } | { ok: false; conflicts: string[] }`.

- [ ] **Step 1: Write failing tests.**
  - A triangle drawn at about 52° and 58° but written 50° and 60° fits to within `FIT_TOLERANCE_DEGREES` of the written values. No point moves more than 5% of the drawing width.
  - A point that no written value touches keeps its exact drawn position.
  - Written lengths of 5 cm and 10 cm on segments drawn 200 and 380 long fit to a ratio of 2 within `FIT_TOLERANCE_FRACTION`.
  - A right mark fits to 90°.
  - A 190° triangle returns `ok: false`, with the conflict message above, and leaves the input unchanged.
  - Values that pass the arithmetic check but can't converge in `FIT_ITERATIONS` return `ok: false`, naming every written value. One example: a right mark and a written 60° on the same angle.
  - A figure with no written values comes back equal to its input.
  - Fitting an already-fitted figure leaves it unchanged (idempotent).
- [ ] **Step 2:** Run the tests. Expected: FAIL.
- [ ] **Step 3: Implement** by iterative projection.
  - Each pass visits every written constraint and makes the smallest move that satisfies it:
    - **an angle:** turn both arms about the vertex by half the error each, keeping their lengths;
    - **a length:** move both ends along the segment by half the error each. The target length is `value / reference.value × the reference segment's current length`, where the reference is the first written length.
  - Stop when every residual is within tolerance, or after `FIT_ITERATIONS` passes.
- [ ] **Step 4:** Run `npx vitest run src/geometry && npm run check`. Expected: PASS.
- [ ] **Step 5:** Checkpoint `feat(geometry): fit figures to their written values`.

### Task 4: What to predict, facts and samples

**Files:**
